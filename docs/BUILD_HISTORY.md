# How PO Dashboard was built

The real order and dates of the work. Every date comes from the dated status line of a plan, the git history, or a
record in this repository.

## Method

Spec first, as with LegalLens: requirements, decisions, architecture, a phased plan approved before any code, tests at
every layer, and an audit of what was built against the requirements. The owner directs and approves; Claude Code
writes the documents and the code and credits itself as co-author on each commit.

| 2026-11-04 | **Status engine (PD-1.3, DEC-36).** The owner settled the rules: evidence wins over a missing step, an invoice counts as goods moved, and a short or zero confirmation stays open and alerts the purchaser that the original PO needs updating, with no ERP integration. All rules are in one pure function, with a thin loader of four queries. 43 tests. 16 deliberate breaks of the rules: 15 caught, and the 16th changes no result (it removes a filter that only saves work). Also fixed a defect from PD-1.1b: `cache_ok` is not inherited, so queries on `Quantity` and `Money` skipped SQLAlchemy's cache. The warning had been in the test output and was missed. 216 tests. |

A real server was exercised over HTTP (bad file listed by row and nothing written; good file imported; upload without the token refused). Upload needs a small script because the page policy forbids inline script, so the by-hand check in a real browser is still owed (the script cannot be tested from here). 97 new tests: 216 before this step, 313 after. |
| 2026-11-04 | **Entering acknowledgements, shipments and invoices (PD-1.4, DEC-38).** Rules in `ledger/events.py`, forms and a history list on the PO page, removal with a reason in place of editing, slip, price and over-billing flags. A real server was driven through acknowledgement, a later promised date, shipment and invoice over HTTP. 55 new tests: 313 before, 368 after. |
| 2026-11-05 | **Early-warning design and the first slice of PD-1.5 (DEC-39 to DEC-41).** The owner's answers reframed the app: it helps the purchaser catch delays before they would alone, nearly all updates come from monitoring email, manual work is a last resort (an end-of-day batch), chasers are drafts a person sends (DEC-07 stands), tracking comes from email (DEC-01 stands), and a weekly QuickBooks export is the last check that closes things out (DEC-41, proposed). Built: list filters with calendars, an expected date per line (the shipment estimate takes over from the promise), late flags, a carrier tracking link. 391 tests pass. A real QuickBooks export was read after the owner confirmed it: it is Windows-1252 text, lists open lines only, and has no line numbers or unit prices; recorded in the plan, no figures kept. |
| 2026-11-05 | **PD-1.5b: Cancelled, settling by hand, timeline.** Cancelled is its own status and counts as done (DEC-39). A timeline lists what happened to each line. 402 tests pass. The "Waiting to confirm" batch screen is next; it waits on the owner's answer on whether receiving closes a line. |
| 2026-11-05 | **PD-1.6: dashboard counts, open-items report, CSV (DEC-42).** Home tiles link to an Open items page that filters by kind of trouble and vendor and downloads as a formula-safe CSV (UTF-8 with a byte-order mark). The tiles and the report come from one list. 429 tests pass. The owner ruled that dates and sent status come only from emails (DEC-41), so lead-time text and the Print column are not read.
